# dev-workflow 실행 절차

`SKILL.md`가 이 스킬을 트리거했고, 실제로 명령 1~5 중 하나를 실행하는
시점에만 이 파일을 읽으세요. 방법론 자체(왜 이렇게 하는지)는 여기 없습니다 —
각 `docs/0X-*/README.md`를 참고하세요.

> **리뷰 모드**: 이 워크스페이스에서는 **작업물을 사용자가 직접 쓰고 Claude는
> 확인한다** ([`.claude/rules/review-mode.md`](../../rules/review-mode.md)). 아래
> 절차에서 "채운다/작성한다"의 주어는 사용자다. Claude는 파일 골격(템플릿 복사,
> 경로 생성, 게이트 로그 블록 붙이기)까지만 만들고, 내용은 질문과 리뷰로 돕는다.

## 명령 1: 새 문제/프로젝트 저장 (1단계)

1. **먼저 사용자가 규모를 정한다** (`docs/00-overview/scope-tiers.md` (`../../../docs/00-overview/scope-tiers.md`)).
   Claude는 결정 트리의 질문을 하나씩 던지고, 사용자가 고른 등급의 근거가 트리와
   맞는지만 확인한다. 전체가 2~5분 안에 끝나면 **즉시처리**로 아무 단계도 안 밟고 끝낸다. 그 외엔
   Xpress/Lite/Full 중 하나를 정하고 이후 단계에 반영한다. 이 결정 트리 중 "표준
   패턴으로 바로 풀리는가?" 질문에 답하려면 여기서 먼저
   `docs/catalog/patterns.md`를 키워드로 훑어본다 (명령 2와 같은 방식) — 별도
   단계가 아니라 이 규모 판단의 입력값이다.

   **1-1. 준비 재료 꺼내 보기 (즉시처리 제외)** — 등급이 정해지면, 이 항목이 밟을 단계에 쓸 참고 자료·스킬·장부 후보를
   단계별 표 하나로 보여 준다(`reference-intake.md` (`../../rules/reference-intake.md`) ⑤). 고르는 것은 사용자이고,
   고른 목록은 사용자가 세션 파일에 "준비 재료"로 적는다. 아무것도 안 골라도 된다.
2. `docs/01-problem-save/`에서 위 규칙으로 트랙 템플릿 목록을 나열한다. 문제
   설명 자체가 트랙을 명백히 가리키면(예: "LeetCode #N" 같은 알고리즘 문제 번호,
   또는 "~앱/서비스를 만들고 싶다" 같은 프로젝트 서술) 그 트랙으로 자동 선택하고
   사용자에게는 "○○ 트랙으로 저장할게요"라고 통보만 한다. 트랙이 무엇인지
   설명만으로 애매하면 그때 사용자에게 고르게 한다. 템플릿이 1개뿐이면 항상 자동 선택.
3. Claude는 세션 파일 골격(4번 경로에 템플릿 복사)만 만들고, **필드는 사용자가 직접
   채운다.** Claude는 인터뷰 기법으로 되묻는 역할이다 — 사용자가 쓴 문장이 약한 곳을
   질문으로 짚고, 사용자가 고쳐 쓴다 — `docs/01-problem-save/README.md` (`../../../docs/01-problem-save/README.md`)의
   "필드는 어떻게 채우는가" 절(Gause & Weinberg의 컨텍스트-프리 질문) 참고.
   질문은 한 번에 다 던지지 않고 **1~2개씩, 답변을 보고 다음 질문을
   좁혀간다** — 진짜 대화처럼. 답변에 "빠르다/편하다" 같은 정성적 표현이
   나오면 그 자리에서 바로 숫자로 되묻는다. 깊이는 등급에 비례한다(Full=4개
   범주 전부, Xpress=성공기준 위주, Lite/즉시처리=생략 — 같은 문서 참고).
   필수 필드가 비어 있으면 다음 단계로 넘어가지 않는다(1단계 IEEE 830 규칙).
   필드를 다 채웠다고 하면 명령 5의 게이트 리뷰(1→2)로 넘어간다. **Full 등급 + 프로젝트 트랙이면 바로 아래 3-1의 PRD 결정을
   반드시 거친다** (`.claude/rules/problem-save-gate.md` (`../../rules/problem-save-gate.md`)).

   **3-1. PRD 결정 (Full 등급 + 프로젝트 트랙만 — 건너뛰지 않는다)**
   - **단독 질문으로 한다.** 위의 "이렇게 이해했는데 맞나요?" 같은 다른 확인과 한 메시지에
     묶지 않는다. 확인을 묶으면 "둘 다 맞아" 같은 포괄적 답이 어느 결정에 대한 것인지
     모호해진다 — 그런 답은 확정으로 치지 않고 다시 묻는다.
   - 선택지는 확장 안 함 / 경량형(5개) / 상세형(11개)이고, 선택 기준은
     `docs/01-problem-save/prd-template.md` (`../../../docs/01-problem-save/prd-template.md`)를 따른다.
     사용자가 앞서 이미 선택을 밝혔다면 그 선택을 기본값으로 두고 확인만 한다 —
     추천으로 뒤집지 않는다.
   - 답을 받으면 세션 파일 게이트 로그의 **"PRD 결정" 칸에 확정일과 함께 기록**한다.
   - 확장하기로 했으면 PRD 섹션을 같은 인터뷰 방식으로 채우고, 섹션마다 상태를
     **확정**(사용자가 확인함) / **초안**(내가 정리, 확인 필요) / **미정**(정보 없음)으로 표시한다.
     초안·미정이 하나라도 남아 있으면 1→2 게이트는 Go가 아니라 Recycle이고, 2단계를 시작하지 않는다.
   - 확장 결정이 나중에 바뀌면 `gates.md` (`../../../docs/00-overview/gates.md`)의
     "앞 단계 결정이 바뀔 때" 절차를 따른다.
4. 완성된 내용을 아래 규칙으로 저장한다. **어디에 둘지 먼저 정한다**:
   알고리즘·학습 트랙처럼 세션 파일 하나로 끝나는 항목은 워크스페이스 루트에,
   자기 산출물(스킬, 코드, ADR, 테스트 기록 등)이 여러 개 생기는 프로젝트는
   `projects/<슬러그>/` 아래에 **같은 하위 경로**로 둔다. 애매하면 사용자에게 묻는다.

   ```
   docs/01-problem-save/sessions/<트랙파일명(확장자 제외)>/<YYYY-MM-DD>-<슬러그>.md
   projects/<슬러그>/docs/01-problem-save/sessions/<트랙파일명>/<YYYY-MM-DD>-<슬러그>.md
   ```

   예: `docs/01-problem-save/sessions/algorithm-track/2026-09-20-two-sum.md`,
   `projects/qa-prep-system/docs/01-problem-save/sessions/project-track/2026-09-24-answer-card-a.md`

   프로젝트 폴더를 새로 만들면 그 안에 `CLAUDE.md`(프로젝트 라우터 — 진행 상태의
   원천이 어디인지, 프로젝트 고유 규칙)와 `README.md`를 둔다. 방법론·규칙·훅은
   복사하지 않고 루트 것을 그대로 쓴다. 프로젝트 전용 스킬은 루트
   `.claude/skills/<이름>/`에 둔다 (Claude Code가 루트에서 스킬을 찾기 때문).

5. 저장한 세션 파일 맨 아래에
   `docs/00-overview/gates.md` (`../../../docs/00-overview/gates.md`)의 "새 문제/
   프로젝트용 게이트 로그 템플릿" 블록을 붙여서 시작한다 (등급 줄과 "PRD 결정" 줄부터
   채우고 1→2 게이트부터 진행). 이게 없으면 이 문제가 어느 게이트까지 통과했는지 남길 곳이 없다.
   단, **Full 등급 프로젝트 트랙은 "PRD 결정"이 확정 기록되고(확장이면 PRD 섹션이 전부 확정)
   나서야** 2단계로 간다.
6. 저장 후 다음을 확인한다: **알고리즘 트랙의 단순 문제는 보통 2단계를 생략하고 바로
   3단계 패턴 분석 (`../../../docs/03-pattern-analysis/README.md`)으로 간다** — 2단계의
   5단계 파이프라인(BABOK/EARS/Planguage/Kano/RTM)은 무거운 프로젝트 트랙용이다
   (`docs/02-problem-analysis/README.md` (`../../../docs/02-problem-analysis/README.md`)의
   "적용 범위" 참고). 프로젝트 트랙이거나 문제가 복잡하면 2단계 (`../../../docs/02-problem-analysis/README.md`)로.
7. `docs/01-problem-save/sessions/README.md` (`../../../docs/01-problem-save/sessions/README.md`)의
   "트래커" 표에 새 행을 하나 추가한다 — `projects/`에 저장한 항목도 트래커는 이 루트
   표 하나만 쓴다 (문제/프로젝트명, 트랙, 등급, 패턴은 아직
   미정이면 "-", 게이트는 "1→2"). 이 표를 그때그때 갱신하지 않으면 나중에 git log를
   전부 뒤져야 전체 목록을 알 수 있다 — 그게 이 표를 만든 이유다.

## 명령 2: 패턴 검색 (3단계)

1. 사용자가 준 키워드/태그로 `docs/catalog/patterns.md`를 검색한다 (grep 방식).
2. 일치하는 항목이 있으면 각 항목의 "언제 쓰는가"/"트레이드오프"를 요약해 보여준다.
3. 없으면 표준 카탈로그로 안내한다 — 알고리즘 트랙은
   `docs/03-pattern-analysis/01-algorithm-paradigms.md`(설계 패러다임 + 구현 기법 패턴
   두 계층 모두 확인), 프로젝트 트랙은
   `docs/03-pattern-analysis/02-architecture-styles.md`.

## 명령 3: 회고를 카탈로그/체크리스트에 반영 (7단계)

1. 사용자가 `docs/07-maintenance/README.md`의 회고 템플릿을 직접 채운다. Claude는
   "어려웠던 점"마다 "왜?"를 한 번씩 되묻는다 — **5 Whys**의 답은 사용자가 쓰고,
   Claude는 답이 사람 탓("내가 부주의했다")에서 멈추면 시스템 쪽으로 한 번 더 묻는다.
   이 항목의 성장 로그 (`../../../docs/00-overview/growth-log.md`) 리뷰 기록을 함께
   펼쳐 두고, 이번 항목에서 반복된 유형이 있었는지 사용자가 먼저 말하게 한다.
2. "새로 배운 패턴"이 나오면 사용자가 `docs/catalog/patterns.md`에 기존 Volere 카드
   형식 그대로 추가하고, Claude는 형식과 근거를 리뷰한다.
3. "놓쳤던 체크리스트 항목"이 나오면 (5 Whys의 근본원인을 반영해서)
   `docs/catalog/checklist.md`에 추가한다. 성장 로그에서 3회 반복돼 승격 대상이 된
   유형도 여기서 같이 올린다.
4. `docs/01-problem-save/sessions/README.md` (`../../../docs/01-problem-save/sessions/README.md`)
   트래커 표에서 이 항목의 행을 "게이트: 1→7 완주"로, "사용한 패턴"/"테스트" 열을
   최종값으로 갱신한다.
5. `docs/00-overview/README.md` (`../../../docs/00-overview/README.md`)의 진행상황
   (Progress Log) 표와 `docs/00-overview/worklog.md` (`../../../docs/00-overview/worklog.md`)에
   오늘 날짜로 짧게 기록한다 (무엇을 했고 다음 세션이 알아야 할 게 뭔지).
6. 검증은 직접 돌리지 말고 `.claude/agents/verify.md` 서브에이전트에 위임해서
   요약만 받는다 (전체 테스트 + 링크 체크).
7. 변경 사항을 git commit한다 — 커밋 메시지에 어떤 프로젝트/문제에서 나온
   교훈인지 명시. 커밋 전 `.claude/rules/git-workflow.md`를 따른다.

## 명령 4: 외부 스킬/MCP 통합 분석

새 공식 스킬·플러그인·MCP 서버를 설치하거나 평가할 때 실행한다. 자세한
규칙은 `.claude/rules/external-integration.md` (`../../rules/external-integration.md`)에
있고, 여기는 실행 순서만 담는다.

0. 사용자가 도구 이름만 줬으면 설치하지 않고 조사해서
   `docs/catalog/external-tools.md` (`../../../docs/catalog/external-tools.md`) "필요할 때 꺼낼 후보"에
   한 줄 적고 멈춘다(규칙 0절). 아래 1~5는 사용자가 들이기로 했을 때 이어 간다.
1. 이 도구가 어떤 경로를 건드리는지(자기 폴더 안쪽뿐인지, `.claude/**`나
   `CLAUDE.md`·`docs/**`까지인지) 확인한다 — **도구마다 다르게**, 일괄
   체크리스트로 넘기지 않는다. 스킬 본문의 지시문, 출처의 나이·유지자, 설명과 내용의 일치도 함께 본다
   (규칙 1번 두 번째 묶음).
2. 우리 `.claude/rules/**`·`hooks/**`·`agents/**`와 겹치거나 충돌하는 게
   있는지 확인한다.
3. 이 도구가 우리 기준 파일(`CLAUDE.md`, `.claude/rules/**`,
   `.claude/hooks/**`, `.claude/agents/**`)을 스스로 고쳤다면, 그대로 받지
   말고 `.claude/rules/consistency.md`의 기준 파일 지도로 검토 후 커밋
   여부를 사람이 정한다.
4. 채택/격리/제거 중 하나로 판정하고
   `docs/catalog/external-tools.md` (`../../../docs/catalog/external-tools.md`)에
   기록한다. 채택이면 `CLAUDE.md` 라우팅 표와 `consistency.md`의 기준 파일
   지도에도 새 행을 추가한다.
5. 이번 항목에서 실제로 이 도구를 썼다면, 명령 3(회고 반영)에서 통합 시점의
   판정이 실사용 후에도 맞았는지 다시 확인하고, 다르면 `checklist.md`에
   반영한다.

## 명령 5: 리뷰 (게이트 리뷰 / 변경 리뷰)

규칙과 판정 형식(막힘/보완/잘한 점, 근거 필수)은
[`.claude/rules/review-mode.md`](../../rules/review-mode.md)에 있다. 여기는 순서만 담는다.

리뷰를 시작하기 전에 Claude는 성장 로그 (`../../../docs/00-overview/growth-log.md`)의
"리뷰어 개선 기록"을 먼저 읽는다 — 지난번에 질문을 잘못한 방식을 반복하지 않기 위해서다.
질문은 `review-mode.md`의 "질문하는 법" 12개 규칙을 따른다.

### 게이트 리뷰 — 사용자가 단계를 넘어가려 할 때

1. 사용자에게 **자기 판정을 먼저** 받는다: Go/Recycle/Hold/Kill + 한 줄 근거.
   세션 파일 게이트 로그에 사용자가 직접 적어도 되고, 대화로 말해도 된다.
   받기 전에는 Claude의 판정이나 지적을 보이지 않는다(앵커링 방지).
2. `gates.md` (`../../../docs/00-overview/gates.md`)의 해당 DoD 항목과, 그 DoD가 가리키는
   `docs/catalog/checklist.md` 절을 한 줄씩 대조한다. **"단계별 보안 점검 체크리스트"의
   해당 단계 항목도 대조한다**(gates.md "보안 점검"). 성장 로그에서 `관찰` 상태인
   유형은 특히 확인한다.
3. 지적을 막힘/보완/잘한 점으로 보인다. 막힘이 하나라도 있으면 리뷰 판정은 Recycle.
3-1. **청중 질문 렌즈** (`review-mode.md` "리뷰 렌즈", 1→2·3→4·6→7에서 특히):
   6슬롯마다 청중이 물을 질문을 하나씩 만들어 보이고, 작업물에 답의 재료가 있는지를
   "있음 / 공백"으로만 표시한다. 답은 사용자가 한다. 공백마다 "채울지 / 공백으로 둘지"를
   묻고 답을 받는다. 공백은 게이트를 막지 않는다. 발표를 앞둔 프로젝트면 이 질문들을
   프로젝트의 `expected-questions.md` 형식(질문 / 답의 재료 / 근거 위치 / 공백)으로
   사용자가 정리하도록 권한다.
4. 게이트 로그의 결정 칸은 **두 판정이 맞춰진 뒤** 사용자가 적는다. 끝까지 다르면
   사용자의 판정을 적되 근거 칸에 "리뷰 판정: X (이유)"를 같이 남긴다. 결정이 Recycle·Hold면
   근거 칸에 해제 줄(누가 무엇을 하면 풀리나, Hold는 언제 다시 보나)이 있는지 확인한다
   (gates.md (`../../../docs/00-overview/gates.md`) "게이트 로그" 규칙, 장부 W-09).
5. 성장 로그 (`../../../docs/00-overview/growth-log.md`)에 리뷰 기록 블록을 추가하고,
   유형 요약 표·판정 차이 표를 갱신한다. 이번 리뷰에서 Claude가 질문을 잘못한 게
   있었으면(사용자 지적 포함) "리뷰어 개선 기록"에도 한 줄 남긴다. 승격(3회)이나 익힘(연속 3회 없음) 조건을
   넘은 유형이 있으면 사용자에게 알린다. 이번 리뷰·작업에서 스킬이 어긋난 순간을 봤으면(안 불림·잘못 안내·내용 빠짐 등)
   성장 로그 "스킬 개선 후보"에 한 줄 남긴다 — 적기만 하고 스킬은 고치지 않는다.

### 변경 리뷰 — 커밋 전, PR을 열었을 때, 또는 세션 시작 훅이 알려줬을 때

1. 범위를 정한다: 커밋 전이면 `git diff --staged`(없으면 `git diff`), 이미 커밋했으면
   growth-log.md의 `last-reviewed` 이후(`git log last-reviewed..HEAD`), PR이면 그 PR의 diff.
2. 파일 경로에 맞는 규칙 파일(`CLAUDE.md` 라우팅 표)을 기준으로 본다 — 코드는
   `implementations.md`(TDD, 테스트 존재), 문서는 `docs-editing.md`(링크, 상태 문구),
   세션 파일은 해당 단계 DoD. 코드 diff는 `karpathy-guidelines` 2·3번(요청 안 한 기능·추상화, 요청과
   이어지지 않는 줄)으로도 보고, 걸리면 **보완**으로 분류한다. 2번 지적은 `ponytail-review` 형식으로 쓴다(`skill-authoring.md`).
3. 테스트·링크 검증은 `verify` 에이전트에 맡기고 결과만 받는다.
4. 지적을 막힘/보완/잘한 점으로 보인다. **고치는 건 사용자가 한다.** PR이면 사용자가
   원할 때만 PR 코멘트로 남긴다.
5. 성장 로그에 기록하고 `last-reviewed:`를 리뷰한 마지막 커밋의 해시로 갱신한다
   (이 갱신은 메커니즘 작업이라 Claude가 커밋해도 된다).
